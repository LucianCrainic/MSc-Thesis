\section{Supercomputers, clusters and nodes}
\label{sec:hpc-primer}

The experimental machine is a cluster: a set of independently booted
\textbf{nodes} connected by a high-speed interconnect and managed as a
single facility.  Each node has its own processors and memory.  A
\textbf{parallel file system} provides shared storage, while a
\textbf{scheduler} allocates nodes and cores to jobs.  The distinction
matters here because the thesis studies a shared-memory effect within one
node, not distributed inference across the cluster.

\figref{fig:workstation-vs-cluster} contrasts this with the machine on
a desk.  The important difference is not size but \emph{addressability}.
Within a conventional shared-memory node, cores access the node's memory
through the processor's load/store address space, although NUMA makes
some paths slower than others.  Memory owned by another node is reached
through an explicit communication mechanism such as message passing or
remote direct memory access.  That boundary introduces network and
software costs that are absent from the same-socket comparison.

\subsection{How a cluster is used}

Access follows a fixed shape that constrains how experiments are
carried out.  A user logs
in to a \textbf{login node}, which is shared, modest, and meant for
editing and compiling rather than for running anything.  Work is then
submitted to a \textbf{batch scheduler}, which on CRESCO8 is Slurm, as
a script that declares what it needs: how many nodes, how
many cores, for how long, from which partition.  The scheduler queues
the request, and when the resources free up it runs the script on the
allocated nodes and returns the output.

Two consequences matter here.  First, although Slurm can provide an
interactive allocation, the reported campaign uses batch scripts so
that every command and environmental observation is archived with the
result.  Anything needed to validate a run must therefore be captured by
the job rather than reconstructed afterwards.  Second, \emph{the
allocation is not the whole machine}.  A job receives specific nodes
from a specific partition, and the properties of those nodes, rather than
the properties advertised for the cluster, are what a result depends
on.  This is why \secref{sec:first-allocation} treats capturing a
machine-readable system manifest as the first task of the first
allocation rather than as housekeeping.

\subsection{Why HPC hardware differs from a desktop}

Nodes in a cluster are built for sustained throughput rather than for
peak responsiveness, and the differences show up in exactly the places
this thesis cares about.  They carry two or more processor sockets, so
memory access time depends on which socket a thread runs on.  They
carry many more memory channels than a desktop, because feeding fifty
or a hundred cores takes considerably more bandwidth than feeding
eight.  They require cooling and power delivery designed for sustained
many-core load; CRESCO8 uses direct water cooling.  And
increasingly they carry \emph{more than one kind of memory}, which is
where this thesis begins.

That last point is the reason a cluster appears in a study of language
model inference at all.  Machines that combine high-bandwidth memory
with a large-capacity memory tier are often deployed as HPC systems.
The available route to the processor is therefore a cluster allocation
even though the question itself is about a single socket.
\chapref{chap:experimental-platform} describes the Xeon Max hardware
and its memory modes first, then the CRESCO8 cluster that provides
access to it.
